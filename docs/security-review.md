# BOBC core implementation review

This record tracks behavior verified from the executable contracts and local tests. It is not an external security audit or a formal proof. The Vyper specialty review is recorded separately under `.vyper-auditor/runs/`.

## Confirmed behavior documented

- BOBC supply follows live position debt plus bad debt. Accrued interest is minted to the Engine and tracked as surplus until fees are burned.
- Collateral, redemption, and liquidation use 18-decimal oracle values and integer flooring. Interest first floors `debt * rate / 1e18`, then floors elapsed-year interest.
- Cashback has a maximum 200 BPS rate, an owner-managed bounded merchant set, and finite preminted inventory. Tiny rebates floor to zero and reject when the configured BPS are nonzero.
- The local mock is 1:1 and has no withdrawal cap. Current [Curve Vault source](https://github.com/curvefi/curve-stablecoin/blob/master/curve_stablecoin/lending/Vault.vy) rejects deposits that mint zero shares and limits `maxRedeem` by available liquidity. The configured Arbitrum deployment's exact bytecode remains unverified until the fork test runs.

## Open review questions

- Some operations that only reduce risk still require a fresh oracle because they call the shared `_checked_rate` helper. This includes repayment, closure, collateral addition, and rate changes. The behavior is documented and tested as implemented; whether oracle downtime should block these actions is a protocol policy question.
- The engine checks oracle positivity and freshness but has no rate deviation bound. Borrowing safety therefore depends on the configured oracle resisting fresh, overstated samples; the local mock only verifies arithmetic and freshness behavior.
- `_ratio` treats each crvUSD unit as one USD and applies only the BOB-per-USD oracle. A crvUSD depeg therefore reduces the collateral's market value without reducing the value used for borrowing, withdrawal, redemption, or liquidation checks. The docs state the one-dollar assumption; the depeg tolerance and response remain protocol risks.
- Underwater liquidation pays no amount above the assets and insurance available. Keeper incentives in that state depend on BOBC market price and external keeper policies; local tests cover debt and insurance accounting, not keeper profitability.
- The configured external vault can limit withdrawals below the value reported by `convertToAssets`; the local mock does not model an asynchronous exit queue or withdrawal cap.
- The engine grants the configured vault a maximum `uint256` crvUSD allowance at construction and has no revocation route. This is a standing trust assumption; a compromised vault could pull idle crvUSD held by the engine.
- Redemption checks the collateral ratio before `withdraw`, then subtracts the shares returned by the vault without checking the resulting ratio again. A fee-enabled vault may burn shares worth more assets than the requested withdrawal and leave a position below `LIQ_CR`.
- Liquidation estimates collateral with ERC-4626 `convertToAssets`, then transfers fixed payout amounts after redeeming shares. ERC-4626 excludes fees and slippage from `convertToAssets`, while `previewRedeem` includes withdrawal fees; a vault that charges exit fees may return less than the amount the engine later transfers. If idle engine assets let transfers succeed, recorded `insurance_assets` may exceed the actual balance; without idle assets, liquidation can revert. The configured vault's exact bytecode and fee behavior need verification at a pinned fork block. See the [ERC-4626 conversion and redemption requirements](https://eips.ethereum.org/EIPS/eip-4626#methods).
- The engine constructor accepts an ERC-20 asset address and checks that it matches the vault, but deposit accounting assumes exact token transfers. A fee-on-transfer asset could make `_pull_deposit` spend idle engine funds, including insurance, to fund the vault deposit; liquidation transfers could also deliver less than their recorded payout. Production deployment uses crvUSD, whose exact-transfer behavior is an external assumption.
- A stale oracle also stops redemption and liquidation, because both paths use `_checked_rate` before acting. The documentation describes this shared freshness gate; its recovery impact depends on oracle uptime and available risk-management paths.
- The forked LlamaLend check is unrun until `ARBITRUM_RPC` is available. The selected fork block is printed by the test and can be pinned with `ARBITRUM_FORK_BLOCK`.
